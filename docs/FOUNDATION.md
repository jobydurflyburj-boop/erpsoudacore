# SoudaCore ERP — Tenancy + Authentication + RBAC Foundation

This is the foundation layer every future SoudaCore module (CRM, Sales,
Purchase, Inventory, Accounting, HR/Payroll, Reports, AI Assistant) will
be built on top of. **No business modules exist in this codebase yet —
that's deliberate.** This foundation is complete and production-ready on
its own terms: a company can register, log in, manage users/roles/
branches/departments, and every table and request is tenant-isolated.

---

## 1. Stack

- **Laravel 12**, PHP 8.3
- **PostgreSQL 16** — chosen specifically for native Row-Level Security
  (RLS), which is the DB-level tenant isolation boundary (see §3)
- **Redis** — cache, queue (Laravel's Redis queue driver), rate limiting
- **Laravel Sanctum** — API token auth, doubling as the "device session"
  primitive (§4)
- **Docker Compose** — app (PHP-FPM), nginx, postgres, redis, a queue
  worker process, a scheduler loop, and mailhog for local email testing

Run locally: `docker compose up -d`, then inside the `app` container:
`php artisan migrate --seed`. The seeder creates the permission catalog,
a bootstrap Super Admin (`superadmin@soudacore.app`), and — local/testing
environments only — a demo tenant (`demo.soudacore.app`) with a working
Company Owner login, so there's something to log into immediately.

## 2. Folder structure — why it's shaped this way

```
app/
├── Multitenancy/TenantContext.php     # request-scoped "which tenant is this" holder
├── Models/
│   ├── Concerns/
│   │   ├── BelongsToTenant.php        # app-layer tenant scoping (global scope + auto-fill on create)
│   │   ├── HasUuid.php                # UUID PKs, generated by Postgres not PHP
│   │   └── Auditable.php              # opt-in model-event → AuditLog wiring
│   └── *.php                          # Tenant, Company, Branch, Department, Role,
│                                       # Permission, User, RefreshToken, OtpCode, ...
├── Repositories/
│   ├── Contracts/*.php                # one interface per aggregate
│   └── Eloquent/*.php                 # the only place Eloquent query code for
│                                       # these aggregates is allowed to live
├── Services/                          # business logic — AuthService, TokenService,
│                                       # RegistrationService, RoleService, etc.
├── Http/
│   ├── Controllers/Api/V1/
│   │   ├── Auth/                      # login, logout, refresh, OTP, password reset, sessions
│   │   └── Admin/                     # users, roles, permissions, departments, branches, companies
│   ├── Middleware/                    # ResolveTenant, EnsureTenantIsActive, CheckPermission, ...
│   ├── Requests/                      # Form Request validation, one per endpoint
│   └── Resources/                     # API Resources — the only place a model is serialized
└── Providers/
    ├── AppServiceProvider.php         # binds TenantContext as a singleton
    └── RepositoryServiceProvider.php  # EVERY interface → implementation binding, nowhere else
```

**The pattern every future module repeats:** a `Contracts/XRepositoryInterface`
+ `Eloquent/XRepository`, a `Services/XService` for anything beyond plain
CRUD, `Http/Controllers/Api/V1/<Module>/`, `Http/Requests/<Module>/`,
`Http/Resources/`, and its own route group in `routes/api.php` guarded by
`permission:<module>.<action>`. Nothing about tenancy or auth needs to be
re-solved by a new module — it inherits `BelongsToTenant` and the RBAC
middleware for free.

## 3. Multi-tenancy — two enforcement layers, not one

> A full audit of every query path — what was verified, what was found,
> and what was fixed — is in `docs/TENANT_ISOLATION_REVIEW.md`. Read that
> alongside this section for the complete picture; this section describes
> the design as it now stands after that review.


**Layer 1 — application scope (`BelongsToTenant` trait):** every
tenant-owned model auto-filters by `tenant_id` on every query and
auto-fills it on create, from `TenantContext`. Convenient, and correct
for the common case, but a trait can be forgotten or bypassed by a bug.

**Layer 2 — PostgreSQL Row-Level Security (the real boundary):** every
tenant-scoped table has `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL
SECURITY` and a policy requiring `tenant_id = current_tenant_id() OR
is_super_admin()` (see the `enable_row_level_security` migration). This
is enforced by Postgres itself, beneath the ORM — `TenantIsolationTest`
proves this specifically by running a **raw** query that bypasses
Eloquent's global scope entirely and showing it still returns zero rows
for another tenant's data.

**How the binding happens:** `ResolveTenant` middleware (runs first on
every API request, see `bootstrap/app.php`) resolves the tenant from the
subdomain (production) or the `X-Tenant-ID` header (local/dev/tests),
sets it on `TenantContext`, and calls `TenantContext::apply()`, which runs
`SELECT set_config('app.tenant_id', ..., false)` against the current DB
connection. From that point in the request, every query — Eloquent or
raw — is bound by RLS. Immediately after Sanctum authentication,
`BindAuthenticatedTenant` middleware then explicitly confirms the
authenticated token actually belongs to that tenant (or, for a request
that resolved no tenant at all, binds the token owner's own tenant as a
fallback) — see `docs/TENANT_ISOLATION_REVIEW.md` Finding 4 for why this
isn't left implicit.

**Tenant → Company → Branch:** a `tenant` is the billing/subscription
account; most tenants have exactly one `company` (legal entity), but the
schema supports more (holding-group structures) — `RegistrationService`
creates one default company + one main branch automatically at signup.
Every business table added by a future module carries `tenant_id`
(required) and typically `company_id`/`branch_id` for finer scoping.

**Email uniqueness is per-tenant, not global** — the same address can be
a Company Owner at one company and an invited Employee at another. This
is why every lookup-by-email in this codebase takes an explicit
`tenant_id` (`UserRepository::findByEmailForTenant`) rather than relying
on a global unique constraint.

## 4. Authentication — how login, sessions, and refresh actually work

- **Access tokens** are Laravel Sanctum tokens, short-lived
  (`config('sanctum.expiration')`, default 60 minutes).
- **Refresh tokens** are a custom addition (`refresh_tokens` table,
  `TokenService`) — Sanctum doesn't rotate tokens natively. Every refresh
  consumes the presented token and issues a new one in the same
  "family". **Presenting an already-consumed refresh token is treated as
  theft** — the entire family is revoked and every device tied to it must
  log in again (`TokenServiceTest::test_reusing_an_already_rotated_refresh_token_revokes_the_whole_family`
  proves this).
- **Multi-device sessions** = the `refresh_tokens` table itself. One row
  per device/login. `GET /api/v1/auth/sessions` lists them,
  `DELETE /api/v1/auth/sessions/{id}` revokes one specific device without
  touching the others.
- **Remember me** extends the refresh token's TTL from 30 days to 90
  (`config/security.php`) — it does not change the access token's TTL,
  which is always short.
- **MFA/OTP** is required for high-trust roles (`Company Owner`, `Admin`,
  `Accountant`, `HR` — see `AuthService::MFA_REQUIRED_ROLES`) as a second
  step after password: `/auth/login` returns `{"status":"otp_required"}`
  with an opaque, single-use `ticket` (never a raw user ID — see
  `docs/TENANT_ISOLATION_REVIEW.md` Finding 5 for why), and
  `/auth/otp/verify` takes that `ticket` + the code to complete the login.
  instead of tokens, and `/auth/otp/verify` completes the login. The OTP
  generation/verification/expiry/attempt-limiting logic
  (`OtpService`) is fully implemented; only the SMS transport is a
  deployment-time config value (`OTP_SMS_DRIVER`), since it needs real
  gateway credentials this environment doesn't have.
- **Super Admin login is a structurally separate flow**
  (`SuperAdminLoginController` → `AuthService::attemptSuperAdminLogin`),
  not a branch inside the tenant-user login. It looks up `users` rows
  where `tenant_id IS NULL` — these are platform accounts, not tied to
  any company. Because RLS default-denies everything without an active
  tenant or `is_super_admin` session flag, this one lookup deliberately
  sets `is_super_admin` on `TenantContext` *before* querying — safe
  because it's fixed backend code (not built from user input), and it's
  the only way to find a Super Admin row at all under RLS's
  default-deny posture.
- **Company registration** (`RegistrationService::registerCompany`) is
  one DB transaction: tenant → default company → main branch → the full
  default role set (`RoleProvisioningService`) → the first user (Company
  Owner), then a verification email is sent. A half-created tenant is
  never left behind by a failure partway through.
- **Forgot/reset password** is a small deliberate reimplementation of
  Laravel's password-broker pattern (`PasswordResetService`), because the
  built-in broker assumes a globally-unique email — ours isn't. Reset
  responses are identical whether or not the email exists, to prevent
  account enumeration. A successful reset revokes every other session for
  that user.

## 5. RBAC — two layers

1. **Module-level** (`roles` + `role_permissions`, checked by the
   `CheckPermission` middleware on every guarded route): can this role
   `view`/`create`/`edit`/`delete`/`approve`/`export`/`print` in this
   module at all. **Database-driven, not hardcoded** — the permission
   catalog lives in `config/permissions.php` (seeded by `PermissionSeeder`)
   and role→permission grants are rows in `role_permissions`, editable
   per tenant via `PUT /api/v1/admin/roles/{role}/permissions`.
2. **Record-level** (left as a documented pattern, not yet needed by any
   route in this foundation): a future module scopes a query by
   `owner_user_id = auth()->id()` for roles that should only see their
   own records — the same `WHERE` clause pattern every module reuses,
   not a separate permission system.

**Default roles** are provisioned automatically for every new tenant by
`RoleProvisioningService::provisionDefaultRoles()`: Company Owner, Admin,
Manager, Sales, Accountant, HR, Inventory, Cashier, Employee — all
editable afterward, none hardcoded into route logic. **Super Admin** is
provisioned once, globally (`tenant_id IS NULL`), by
`provisionSuperAdminRole()`, and holds every permission in the catalog.

**Why most default roles start with zero grants:** the only modules that
exist today are `admin` and `core` (see `config/permissions.php`) — CRM,
Sales, Inventory etc. don't exist in this codebase yet, so there's
nothing yet for a Sales or Cashier role to be granted. The role exists
and is ready; a future module adding its permission block to
`config/permissions.php` and its grants to
`RoleProvisioningService::defaultGrantMatrix()` is the only change needed
to make that role useful — no route, middleware, or migration changes.

## 6. Security features implemented (not just listed)

| Requirement | Where |
|---|---|
| UUID primary keys | `HasUuid` trait, Postgres `gen_random_uuid()` default |
| Soft deletes | `SoftDeletes` on every user-facing model |
| Audit logs (field-level diffs) | `Auditable` trait → `AuditLogService` → `audit_logs` table |
| Activity logs (behavioral events) | `ActivityLogService` → `activity_logs` table |
| Rate limiting | `LoginRateLimiter` (per email+tenant AND per IP, both must pass); Laravel's `throttleApi` on the whole API |
| CSRF | N/A by design — stateless Bearer-token API, not cookie-session based, which is largely CSRF-immune; Sanctum's CSRF middleware is configured for the SPA-cookie case if ever needed |
| XSS | JSON-only API responses (never renders HTML from user input); frontend's responsibility to escape on render |
| SQL injection | Eloquent/query builder parameterized queries exclusively — no raw string-concatenated SQL anywhere in this codebase |
| Failed login tracking | `failed_login_attempts` table, written by `LoginRateLimiter::recordFailure` |
| Password history | `password_histories` table, `PasswordPolicyService` — last 5 (configurable) passwords can't be reused |
| Device tracking | `user_devices` table (durable, survives logout) distinct from `refresh_tokens` (session-scoped) |
| Password policy | `PasswordPolicyService::rule()` — 10+ chars, checked against known-breached corpora, no arbitrary composition rules (OWASP guidance) |

## 7. API conventions

- Every route is under `/api/v1` (see `routes/api.php`).
- Every non-2xx response is `{"error": "...", "message": "...", "details": {...}}`
  — one shape, enforced centrally in `bootstrap/app.php`'s exception
  handling, never per-controller.
- List endpoints support filtering/sorting/searching via
  `spatie/laravel-query-builder`, allow-listed per repository
  (`$allowedFilters`, `$allowedSorts`, `$searchableFields` in each
  `Eloquent/*Repository`) — never open-ended, so a client can't filter on
  a column that wasn't deliberately exposed.
- Every mutating endpoint is behind a Form Request — validation is never
  inline in a controller.

## 8. Testing

`tests/Feature/Tenancy/TenantIsolationTest.php` is the most important
test in this codebase — it proves cross-tenant isolation holds even when
Eloquent's global scope is deliberately bypassed, i.e. that RLS (not just
app-layer discipline) is the real boundary. `tests/Feature/Rbac/` proves
permission grants/denials actually gate requests. `tests/Unit/` covers
token rotation-on-reuse and password-history rejection in isolation.

**Tests require real PostgreSQL**, not SQLite — RLS, `citext`,
`gen_random_uuid()`, and the partial unique index on Super Admin emails
are all Postgres-specific, and SQLite would silently pass tests that
prove nothing (see `phpunit.xml`'s comment). Point `DB_DATABASE` at a
disposable `soudacore_testing` database; `RefreshDatabase` migrates it
fresh on every run.

## 9. What's explicitly NOT in this foundation

Per the brief: no CRM, Sales, Purchase, Inventory, Accounting, HR/Payroll,
Reports, or AI Assistant routes/tables/models exist here. Also
out-of-scope for this pass, flagged rather than faked:

- SMS gateway integration for OTP delivery (`OtpService` is complete;
  only the `unifonic`/`msegat` driver cases are unimplemented — see the
  `TODO(ops)` in that file and in `.env.example`).
- "New device" login notification email (detection logic in
  `DeviceService` is complete; the notification content/channel is a
  product decision, flagged with a `TODO(notifications)`).
- Record-level (row-owner) permission scoping — documented as a pattern
  in §5, not yet needed since no module has "my own records vs.
  everyone's" data yet.
