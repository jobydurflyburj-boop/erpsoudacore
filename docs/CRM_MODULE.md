# CRM Module — Sprint 1: Lead Management Foundation

Built strictly on the existing foundation — no architecture changes.
Same repository/service/controller/request/resource shape as Platform
Administration, extended with one genuinely new pattern (`LeadPolicy`)
and one reusable utility (`SequenceService`) both explained below.

**Scope delivered:** CRM Navigation, CRM Dashboard, Lead Management,
Lead Source Management, Lead Status Management, Lead Assignment, Lead
Activity Timeline. Opportunities, Customers, Quotations, Meetings,
Tasks (CRM-specific), and Reports are explicitly Sprint 2+.

---

## New tables (all RLS-protected from their first migration)

`sequence_counters`, `lead_sources`, `lead_statuses`, `leads`,
`lead_activities`, `lead_attachments`. See the `2025_03_01_*` migrations.

## Lead numbering — a reusable pattern, not a one-off

`SequenceService` is a generic per-tenant atomic counter
(`sequence_counters` table, one row per `(tenant, name)`), not something
built specifically for leads. `UPDATE ... RETURNING` under a transaction
serializes concurrent callers for the same counter without an
application-level lock. Every future module needing a human-readable
sequential number (invoice, PO, etc.) reuses this exact service — that's
the point of building it generically now rather than inlining a
lead-specific counter.

## Lead Sources / Lead Statuses — same pattern as Roles

Database-driven, per-tenant, fully editable — not hardcoded. Seeded with
sensible defaults (`CrmProvisioningService`) at tenant registration,
exactly the same role `RoleProvisioningService` already plays for RBAC.
Existing tenants (registered before this module existed) are backfilled
via `php artisan crm:provision-defaults` (idempotent — safe to re-run).

Lead Statuses carry `is_won`/`is_lost`/`is_default` flags the dashboard
and lead-creation flow both depend on — deleting the current default is
blocked, and setting a new default atomically clears the previous one.
Deleting a source/status still in use by a lead is blocked with a 409 —
worth noting *why* the obvious DB-level protection doesn't apply here:
both tables are soft-deletable, so `leads.lead_source_id`'s
`ON DELETE` behavior never actually fires (a soft delete is an `UPDATE`,
not a `DELETE`) — the in-use check is explicit application logic, not a
caught database exception.

## Record-level scoping — the pattern the foundation described, now real

The foundation's docs described but never needed record-level RBAC
scoping ("Sales sees only their own records"). This module is the first
to need it: `Lead::OWN_RECORDS_ONLY_ROLES` (currently just `Role::SALES`)
get their lead visibility and edit rights narrowed to
`assigned_to_user_id = self`, on top of the same `crm.*` module-level
grant everyone else with CRM access has. Two places enforce this
consistently:
- `LeadController::index` scopes the base query.
- `LeadPolicy` (new — the first `Illuminate\Auth\Access` Policy in this
  codebase) scopes single-record `view`/`update`/`delete`/`assign`,
  registered via `Gate::policy()` in `AppServiceProvider`.

This is additive, not a replacement for `CheckPermission` middleware —
the route-level `permission:crm.*` gate still answers "can this role
touch leads at all" (fast, no row needed); the policy then answers the
record-level question once a specific `Lead` is loaded. Both run.

## Lead Activity Timeline

Every meaningful lead event lands in `lead_activities`: creation, status
change, (re)assignment — all system-generated by `LeadService` — plus
manually logged touchpoints (call/email/whatsapp/note) via
`POST /crm/leads/{lead}/activities`. This is the record-level equivalent
of `activity_logs` (module-wide feed) — a per-lead feed a salesperson
actually works from, not a compliance log.

## CRM Dashboard — real data, honestly scoped

Every figure is a live query against `leads` — no placeholders. Totals,
pipeline-by-status breakdown, breakdown by source/priority, and recent
leads are all real from the moment this migrates. Scoped the same way
lead visibility is: a Sales user's dashboard reflects only their own
leads, not the whole company's.

## A real bug found and fixed while building this sprint

`Controller::ok()` had a special case —
`is_array($data) ? $data : ['data' => $data]` — meant to let call sites
that had already manually wrapped their response avoid double-wrapping.
In practice it silently skipped the `{"data": ...}` envelope for **every
plain-array response**, which turned out to be most message-only
responses (login, password reset, email verification, etc. — present
since the foundation) and both dashboard endpoints' composite payloads
(Platform Admin's and this module's). `response()->json($data)` with a
plain PHP array sent that array as the literal JSON root — e.g.
`{"widgets": ..., "charts": ...}` instead of the documented
`{"data": {"widgets": ..., "charts": ...}}`.

Fixed at the root (`ok()` now always wraps unconditionally) rather than
patching call sites individually — the three controllers that had
manually pre-wrapped (`CompanySettingsController`,
`NotificationPreferenceController`, `CrmNavigationController`) were
updated to stop, so they don't now double-wrap. `ApiResponseEnvelopeTest`
pins both shapes (message-only and composite-array) as a regression test.
This also means the Platform Administration sprint's dashboard tests,
which asserted `data.widgets...`, were asserting the *intended* shape
all along — they just would have failed against a real server before
this fix, since nothing in this environment runs the suite against a
live Postgres instance to catch it at build time.

## What's still deferred

No Opportunities, Customers, Quotations, Meetings, CRM-specific Tasks, or
Reports — Sprint 2+ per the brief. Nothing in this sprint anticipates
their schema; adding them is new tables + new modules in
`config/permissions.php`, the same extension pattern this module itself
followed.
